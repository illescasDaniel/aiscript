API and agent providers

Choose native API providers or locally installed ACP agents for script generation and AI calls made by generated scripts.

Review only. The walkthrough is a simulation. Approval happens in chat.

At a glance

First-time selection → two provider families

Text equivalent: on first interactive setup the user selects a provider using local availability hints; aiscript then passes a neutral request to its providers subpackage, which calls a native API or local ACP agent and returns a normalized result and its effective guarantees. Failures do not trigger a silent fallback.

  • First use: when neither current nor legacy config exists, interactive --init or provider-requiring generation offers a provider menu. Existing configs keep their behavior; --ask, cached runs, help/list and non-interactive use never prompt.
  • Availability hints: inspect executable presence on PATH and presence of relevant environment keys only. A hint is not a login, authentication or connectivity check; unavailable and unknown choices remain selectable.
  • Persistence: publish a complete private config atomically without clobbering a concurrent creator; cancelled selection creates no config. New starter YAML includes commented provider/model examples after OpenAI.
  • Outcome: select Anthropic or Gemini APIs, or built-in ACP names such as claude-acp and codex-acp, for generation and --ask, subject to required capabilities and explicit verification. Existing OpenAI configurations stay usable.
  • ACP: launch an already installed, authenticated agent; no automatic installation. Deny requested permissions initially and do not claim that denial sandboxes the agent; revisit useful tools later.
  • Shared package: an internal aiscript.providers subpackage gives API and ACP adapters a common request, result and error format, while exposing differing capabilities. It remains inside the current distribution; a separate release is an optional future goal, not a promise.
  • ACP --ask (Q7 A approved): validate JSON locally; deny permission requests without claiming no tools; use local byte/time limits without promising a model-token cap or system-role instruction. Existing API guarantees remain unchanged.
  • Failure paths: F1 configuration; F2 authentication; F3 missing, crashed, or incompatible process/API; F4 permission; F5 bad output; F6 limits; F7 cancellation; F8 invalid input or menu cancellation; F9 config creation/race; F10 availability unknown. No silent provider fallback.
Resolved questions (3)

  3. Q10. If AISCRIPT_PROVIDER is set during onboarding, should it govern the current generation or be suppressed? Recommend preserving its current-generation override, disclose the different provider, and persist the menu selection for --ask and later defaults.

Detailed report

Flow and boundaries

A user invokes script generation or calls aiscript --ask; aiscript resolves the selected provider and dispatches through a shared aiscript.providers subpackage. The package accepts a provider-neutral request and returns normalized results or bounded errors, with explicit capabilities and effective guarantees; matching formats do not imply identical provider semantics. Provider-specific API and ACP adapters sit behind that boundary. A native API adapter exchanges messages with the chosen service; an ACP adapter starts a locally installed agent, negotiates ACP and sends a prompt. The adapter normalizes the final response; structured results are validated locally before being returned. The application retains configuration, CLI, output validation, call counters, secret scanning, review and confirmation; provider code does not depend on application modules. The generated-script shim remains independent of the provider package. The existing reviewer behavior remains unchanged. The current generator uses llm.chat; --ask already has a neutral provider contract but its target and composition are OpenAI-specific. Both config resolver paths currently reject a selected provider absent from a nonempty providers mapping, so built-in selection needs an explicit compatibility rule.

Example: default_provider: claude-acp needs no providers: entry. The agent must already be installed and logged in. Its billing and eligibility come from its provider; ACP itself does not grant a subscription or guarantee that a provider permits a particular use. Native API credentials remain configured separately. Exact connector commands, supported login methods, model overrides, terms, and behavior need verification before implementation.

Text equivalent: User → aiscript resolver → shared providers subpackage and its API/ACP adapter → external provider. F1 through F7 are described in the failure inventory below. Canonical system diagrams: system design.

Package boundary and future extraction

The shared subpackage belongs to the existing aiscript distribution and exposes neutral request, result and error concepts rather than SDK-specific objects. Explicit capabilities and effective guarantees reveal ACP differences; caller policy stays in aiscript, not in the transport. Separate packaging, independent versioning, a stable public API and publication are deferred decisions. Internal boundaries and isolated tests can make future extraction practical, but this design does not promise a separate release or API stability.

Failure inventory and recovery

  • F1: Invalid configuration or unknown name: return actionable config error before dispatch; fix config.
  • F2: Credentials missing, expired or rejected: return auth error without leaking secrets; authenticate agent or configure API credential.
  • F3: Executable missing, startup or handshake fails, process exits, incompatible version, API unavailable: return provider error; install or repair separately and retry.
  • F4: ACP permission request: deny; do not grant terminal or filesystem proxy access. If agent cannot finish, return error. Denial is not an operating-system sandbox: agents can have independent filesystem, network, tools and inherited environment access.
  • F5: Unsupported required capability, malformed, incomplete or schema-invalid response: fail clearly; do not report partial output as success. Retry or choose a compatible provider.
  • F6: Timeout, output/resource cap, quota or rate limit: report a bounded error, stop work and clean up; retry only according to existing safe policy. Exact budgets and costs require measurement and spec decisions.
  • F7: User cancels: cancel request and clean up owned subprocesses; return cancellation without success. External side effects already made by the agent cannot necessarily be undone.
  • F8: Invalid first-use input prompts a retry; cancellation leaves no config and no provider call.
  • F9: Config preparation, publication or concurrent creation fails: do not clobber another config or report a partial file as success; report the outcome and recover using the existing configuration where specified.
  • F10: Local detection is unavailable or inconclusive: label availability unknown, permit selection, and give no claim about login or connectivity.

Traceability before spec: success and F1–F10 each need one or more scenarios and verification in the Spec tab.

Design decisions and preferred resolution

  • Success criteria: Native Anthropic/Gemini API choices work through generation and --ask where their contracts are met; built-in ACP choices work through generation and --ask, subject to required capabilities; OpenAI and configured compatible endpoints remain usable. Each connector is considered supported only after real verification.
  • Failure and recovery: F1–F10 return actionable bounded errors; no silent fallback to a different provider, no partial result treated as success.
  • Performance and resources: bound startup, request time, output, concurrency and process lifetime; measure realistic provider startup and response times before proposing numbers. ACP may incur startup latency and subscription consumption.
  • Trust and validation: protect secrets and logs; expand known-secret detection and existing reviewer redaction for native provider credentials, including Google key formats. Validate config, protocol events and requested structured output. Deny ACP permission requests. A locally installed agent remains a trusted executable with its own OS, network, environment, hooks and configuration privileges; approval here does not establish isolation.
  • Compatibility and rollout: preserve existing provider configuration and reviewer behavior. Existing explicit definitions take precedence over built-ins to preserve behavior; document the collision. Release providers in verified increments; installing or authenticating an agent remains the user's responsibility.

Contracts and decisions

Project-required companion: Markdown specification; the page is the visual review source and the companion carries the project’s canonical Markdown spec. Exact adapter interfaces belong at the architecture gate.

  • Success: native and individually qualified ACP selections support script generation and --ask. The provider package normalizes requests, outcomes and errors, exposes effective guarantees, and has no application-layer imports. Its independent publication is deferred.
  • Failures and recovery: preserve existing CLI/Python errors, refuse partial success and cross-provider fallback, deny ACP permission/filesystem/terminal requests, do not replay ACP prompts, and reap owned processes after failures or cancellation.
  • Performance and resources: retain existing input and call limits. Proposed acp.timeout_seconds is a total ACP request deadline for both generation and ask (default 100 seconds; range 1–600). acp.max_frame_kib and acp.max_response_kib bound an individual frame and aggregate answer text (each default 1024 KiB; range 1–16384). Invalid types, booleans and values outside range fail before dispatch. Existing API per-attempt timeout and retries stay unchanged. Bounds are not model-token or billing limits.
  • Trust and validation: APIs retain their existing guarantees. ACP prompts may lack a system role; strict model decoding and a model output-token cap are not guaranteed. Deny permission and client filesystem/terminal requests, validate JSON locally, and disclose that an agent has independent operating-system privileges. Do not log secrets, prompts, raw payloads or agent stderr; include known native credential variables in secret detection.
  • Compatibility and rollout: explicit configured definitions win; unrelated entries do not disable built-ins. Generation honors its existing environment selection override; --ask continues to select YAML only. Each connector is declared supported only after real qualification. Installing agents, login, separate package publication, arbitrary ACP commands, automatic tool grants and sandboxing are out of scope.

Live ask notice: After validation and successful call-cap claim, immediately before provider invocation, emit exactly one timely stderr line to direct --ask and Python aiscript.ask() callers. ACP shows the configured total deadline, including 120 if configured to 120; APIs state the per-attempt timeout and that retries may take longer. The Python shim exposes this trusted status while the request runs without forwarding raw child or agent stderr, prompts, inputs or credentials. No status enters stdout or the answer. The approved Q13 decision emits no notice if validation or call-cap preflight fails.

Native structured output: provider-side strict schema support for the existing supported subset must be requested and honored, or the call fails clearly; local validation alone does not satisfy the existing API contract.

Starter YAML: new starter configs show commented provider examples after OpenAI. Native model fields may be demonstrated where supported; ACP model choice follows the agent’s configuration unless a later approved contract adds an override. Existing files are preserved. ACP model overrides remain deferred; provider model choice uses the agent configuration.

First use: Interactive --init and provider-backed generation show a list when neither current nor legacy configuration exists. --ask, help, version, list, cached execution, and non-interactive calls do not prompt; non-interactive --init retains its OpenAI template. Detect only PATH executable and key-environment presence, without displaying secret values or starting processes, authentication, installation, or network calls. Status indicates detection, not readiness; all choices remain selectable.

Invalid input reprompts and cancellation or EOF publishes nothing. Prepare a complete private temporary file and atomically publish without clobbering: on a creation race preserve and load the winning config; on write failure leave no partial destination. Preserve existing --init permission behavior. If AISCRIPT_PROVIDER is set, disclose its priority for current generation; persist the selection for --ask and subsequent defaults without the override. vLLM support is future work and outside this feature.

Acceptance scenarios

S1 · Native API generation

Given Anthropic or Gemini is selected and configured with a valid credential and model, When a user requests a script, Then the chosen API receives the request and the returned script goes through existing scanning, review and confirmation before save.

S2 · Native API ask

Given a supported native API and a valid text or supported-schema ask, When a generated script calls ask, Then it returns text or locally validated JSON while requesting the existing provider-side strict-schema and output-token controls when applicable.

S3 · ACP generation

Given a qualified installed and authenticated ACP agent selected by built-in name without a provider entry, When generation succeeds, Then its text passes the existing script review and save pipeline.

S4 · ACP ask

Given a qualified ACP agent selected by built-in name, When a script requests text or a supported schema, Then aiscript returns the final text or locally validated JSON and applies the documented ACP-specific Q7 A limitations.

S5 · Selection precedence (F1)

Given unrelated provider entries and a built-in selection, When resolution runs, Then the built-in resolves; an explicit same-name entry wins, and an unknown or invalid name fails before a provider call.

S6 · Authentication (F2)

Given missing, expired or rejected API or agent credentials, When the provider is invoked, Then it returns sanitized setup guidance without exposing credentials, with no fallback.

S7 · Connector unavailable (F3)

Given a missing executable, incompatible handshake, malformed frame, unexpected exit or unreachable API, When a request runs, Then it fails with an actionable bounded error, discards partial output and reaps any owned process.

S8 · Permission requests (F4)

Given an ACP agent requests client permission or a filesystem or terminal callback, When aiscript handles the request, Then it denies it without an interactive grant and accepts a response only if the agent still completes successfully.

S9 · Invalid or unsupported output (F5)

Given malformed JSON, schema mismatch, incomplete output or an unsupported required API capability, When output is interpreted, Then aiscript returns an output or capability error, emits no partial answer and does not retry the prompt.

S10 · Refusal and empty answer (F5)

Given a provider refuses or returns no usable answer, When ask interprets the response, Then a refusal returns the existing refusal category (exit 7) and an empty or unusable answer returns the existing invalid-output category (exit 8), with no successful output.

S11 · Deadline and size boundaries (F6)

Given an ACP request exceeds its configured total deadline, an individual frame exceeds its configured frame cap, or aggregate answer text exceeds its configured response cap, When the limit is reached, Then aiscript stops, discards partial output, returns an error and reaps the process.

S12 · Rate or quota limit (F6)

Given the selected provider reports a rate or quota limit, When the call fails, Then aiscript reports the appropriate existing failure category, does not switch provider and does not replay an ACP request.

S13 · Cancellation (F7)

Given a running ACP request, When the user cancels, Then aiscript requests cancellation where available, terminates and reaps its owned process, and does not return partial success; already completed external actions may persist.

S14 · Input and call limits

Given ask input at or above its configured size limit, invalid UTF-8, invalid schema or an exhausted per-run call cap, When ask is invoked, Then it returns the existing validation or cap error without sending a provider prompt.

S15 · Distinct routing

Given YAML selects one provider and an aiscript routing environment override selects another, When generation and ask resolve their providers, Then generation preserves its existing environment precedence and ask uses YAML only; agent-owned configuration is separately documented.

S16 · Secret handling

Given a supported Anthropic or Gemini credential exists only in a recognized environment variable, When secret scanning and failure diagnostics execute, Then known credential values are detected and never echoed in diagnostics or raw provider payloads.

S17 · Starter configuration

Given a new initialization, When starter YAML is generated, Then it lists the native and five ACP choices after OpenAI as valid commented examples, includes representative native models and ACP agent-default guidance, and leaves ACP built-ins usable without entries; existing file contents are not rewritten.

S18 · Qualification and shared boundary

Given a candidate connector and the shared provider boundary, When release support is claimed, Then real connector qualification evidence exists for its documented platform, authentication, routing, output and cancellation, and neutral request/result/error shapes expose effective capability differences without application or shim imports.

S19 · First-use provider selection

Given an interactive initialization or provider-backed generation with neither current nor legacy config, When the user selects a listed provider, Then the complete private starter config is published with that YAML default and the requested operation continues, subject to its normal prerequisites.

S20 · Existing, legacy and unattended invocations

Given an existing or legacy config, a non-interactive invocation, `--ask`, an informational command or cached execution, When aiscript runs, Then it displays no onboarding menu, preserves existing config contents and follows the existing routing and non-interactive behavior.

S21 · Invalid input and cancellation (F8)

Given the first-use menu, When a user enters an invalid selection, Then the menu reprompts; When the user cancels or input reaches EOF, Then onboarding exits without publishing a config or a partial destination file.

S22 · Atomic publication and race (F9)

Given a complete private temporary config, When publication fails, Then the error is reported and no partial destination remains; When another process creates the destination first, Then its contents are preserved and loaded rather than overwritten.

S23 · Advisory detection (F10)

Given an agent or API key is not detected or local detection is unavailable, When the first-use menu is displayed, Then its status is shown as not detected or unknown without asserting authentication, and the provider remains selectable; no network call, agent launch, login, install or secret value disclosure occurs.

S24 · Environment override at onboarding

Given first-use selection saves one provider and `AISCRIPT_PROVIDER` names another, When generation proceeds, Then the current generation uses the environment override with disclosure, while ask and later defaults without the override use the saved YAML choice.

S25 · Starter example activation

Given a newly created starter config containing commented provider examples after OpenAI, When a user follows the documented instructions for a native API or built-in ACP selection, Then the YAML remains valid, the chosen default resolves, and an ACP selection needs no uncommented provider entry or aiscript model override.

S26 · Configurable ACP limits

Given ACP limits omitted from config, When generation or ask resolves settings, Then the total deadline is 100 seconds and each size cap is 1024 KiB; Given valid configured alternatives, When either entry point runs, Then it applies those values, while invalid, boolean or out-of-range settings fail before launching or calling a provider.

S27 · Live ask timeout notice

Given a valid ask and a successful call-cap claim, When direct `--ask` or Python `aiscript.ask()` starts an ACP provider call, Then exactly one status line reaches stderr before completion and displays the configured total deadline, including 120 when configured to 120; stdout and the returned answer contain no notice.

S28 · API timeout notice and safe failure

Given a valid API ask, When the provider call starts, Then exactly one timely stderr notice states its configured per-attempt timeout and that retries may take longer; Given a validation failure or exhausted call cap, When no provider call starts, Then no provider-call notice is emitted, and child/agent stderr, credentials and input data are not leaked.

  • Configuration resolves provider kind and preset, existing explicit-entry precedence, current-generation environment overrides and YAML-only --ask routing. The application owns key origin/endpoint policy; new credential names are included in secret detection and redaction.
  • Adapters return neutral outcomes and capability flags rather than SDK objects. A native API must request strict schema and token limits where required; ACP instead uses the approved local validation and byte/time bounds, with no promise of system role, zero internal tools or a model-token cap.
  • ACP launch uses a fixed executable mapping and argument vector, drains protocol/stdout/stderr safely, denies client permission and filesystem/terminal requests, never replays prompts automatically and cleans up owned processes. Discard partial output on error or cancellation.
  • The shim continues to call the application process without importing the provider package. Convey one trusted status before dispatch while concurrently draining bounded streams; never forward raw child or agent stderr, credentials, prompt data or payloads.
  • Interactive first-use detection checks only PATH and key-variable presence. Config publication stages complete private contents and atomically publishes without clobber; a concurrent winner is preserved and loaded. Existing and legacy configs retain established permissions behavior.
